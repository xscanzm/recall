# 19. Recall 产品体验升级统一规格

本文档是给 AI coding agent 使用的产品体验升级执行规格。

目标：在不推翻现有后端和 AI Pipeline 的基础上，把 Recall 从“工程化记忆后台”升级为一个普通用户愿意每天打开、能看懂、能获得实际帮助的桌面记忆助理。

重要说明：

- 本文档是当前阶段的最高产品体验指导。
- 之前的 11-18 号体验参考文档已删除，不再作为执行依据。
- 不采用过度诗意、过度拟人、过度动画化的表达。
- 不修改 Recall 的根定位：它是基于视觉模型和大语言模型的桌面上下文记忆助理。
- 本阶段重点是前端体验、信息架构、AI 输出对象和日报价值闭环。

## 1. 产品升级目标

### 1.1 当前问题

当前实现后端能力较强，但前端容易呈现为工程系统：

- 页面像后台管理工具。
- 用户看到的是数据对象，而不是“今天发生了什么”。
- AI 输出偏事实抽取，不够服务前端体验。
- 日报、周报价值没有被放到足够显眼的位置。
- 时间记录如果直接呈现，容易像监控或考勤。
- 普通用户不理解 L0、L1、L2、Fact、Scene 等技术概念。

### 1.2 升级目标

Recall 应该让用户每天打开后快速获得三个答案：

1. 我今天到底做了什么？
2. 还有哪些事情没收尾？
3. 我可以怎样把今天整理成自己看的复盘和给别人看的日报？

同时，Recall 要把每天积累的内容沉淀为长期记忆：

- 周报
- 月报
- 项目回顾
- 人物记忆
- 决策历史
- 过去资料找回
- “我上次做到哪了”

### 1.3 核心产品结构

Recall 的体验主线为：

```text
今日时间轴
  -> 今日总结
  -> 待收尾
  -> 我的复盘
  -> 工作日报
  -> 长期记忆
```

用一句话定义：

> Recall 用一条清晰、温和的今日时间轴帮用户回忆一天，再把一天整理成待收尾、个人复盘、工作日报和长期记忆。

## 2. 不采用的方向

Coding agent 不要实现以下方向：

- 不使用“今日颂歌”“时光脉络”“深海沉浸”“心流年轮”“护盾光幕”等命名。
- 不把 UI 做成诗意概念展览。
- 不把提示词写成过度抒情或鸡汤。
- 不实现复杂粒子吸入、光幕墙、果冻动效作为 MVP 必需项。
- 不承诺“所有数据不经过云端 AI”，因为 Recall 的模型能力来自用户配置的视觉模型和 LLM API。
- 不把“用户手动勾选”作为所有记忆生成的前提。
- 不默认展示截图墙或完整屏幕回放。
- 不把半小时切片直接做成考勤表。

可以吸收的方向：

- 前端要有呼吸感、温度和精致感。
- 时间轴不要有监控感。
- 日报要分自己看和给上司/团队看。
- 生成工作日报前，用户应该能选择参与生成的内容。
- AI 输出要更适合前端呈现，而不是只服务数据库。

## 3. 信息架构

### 3.1 主导航

MVP 推荐导航：

1. 今日
2. 待收尾
3. 报告
4. 项目
5. 记忆库
6. 人物
7. 设置
8. 信任中心

如果开发周期紧，第一阶段至少完成：

1. 今日
2. 待收尾
3. 报告
4. 项目
5. 记忆库
6. 设置/信任中心

### 3.2 页面职责

#### 今日

用户每天打开 Recall 的第一屏。

职责：

- 展示今日时间轴。
- 展示今日主线。
- 展示待收尾。
- 展示今日成果、决策、资料。
- 提供“我的复盘”和“工作日报”生成入口。

#### 待收尾

不是传统任务管理页，而是帮助用户找回未完成、未确认、可能要继续的事情。

职责：

- 展示今天和近期未完成事项。
- 展示 AI 认为可能未收尾的工作线程。
- 支持用户确认、完成、忽略、稍后、改项目。

#### 报告

用户拿到直接价值的页面。

职责：

- 生成我的复盘。
- 生成工作日报。
- 生成周报。
- 生成月报。
- 查看历史报告。
- 编辑、复制、导出报告。

#### 项目

长期价值页面。

职责：

- 展示每个项目的进展脉络。
- 展示项目相关任务、决策、资料、人物。
- 支持生成项目周报或项目复盘。

#### 记忆库

找回过去的入口。

职责：

- 搜索过去的事实、场景、任务、项目、报告。
- 支持自然语言搜索。
- 结果要按用户能理解的方式呈现，不要像数据库记录。

#### 人物

可以后置，但应保留产品结构。

职责：

- 记录用户与某个人相关的项目、承诺、讨论和历史上下文。
- 不做监控别人，只做用户自己的关系记忆。

#### 设置/信任中心

职责：

- 模型配置。
- 截图保留策略。
- 黑名单应用。
- 暂停和删除数据。
- 通知设置。
- 数据导出。
- 清晰解释 Recall 看到什么、保存什么、如何调用模型。

## 4. 今日页布局

今日页是本阶段最重要的页面。

### 4.1 总体布局

采用三栏结构：

```text
左侧导航
  中间主区域：今日时间轴
  右侧结果面板：今日总结、待收尾、复盘和日报入口
```

比例建议：

- 左侧导航：64-88px 或固定窄栏。
- 中间时间轴：主宽度，占 60%-70%。
- 右侧结果面板：320-420px。

### 4.2 中间：今日时间轴

今日时间轴是主视觉。

它回答：

- 今天从什么时候开始工作？
- 一天中有哪些自然工作片段？
- 哪些片段是工作、沟通、查资料、写作、开发、会议、休息？
- 每个片段产生了什么价值？

不要直接展示：

- 应用占比百分比。
- 冷冰冰的进程名列表。
- “闲置 25 分钟”这种容易制造焦虑的标签。
- 每半小时固定一格的监工式时间表。

应该展示：

- 自然工作片段。
- 柔和的时间锚点。
- 片段标题。
- 片段摘要。
- 相关项目。
- 产生的待办/决策/资料。
- 可用于日报的标记。

### 4.3 右侧：结果面板

右侧结果面板不是辅助装饰，而是把时间轴转化为结果。

模块顺序：

1. 今日主线
2. 待收尾
3. 今日成果
4. 今日决策
5. 我的复盘
6. 工作日报
7. 明天接着做

右侧面板要始终告诉用户：

> 我已经帮你从今天的活动里整理出了什么。

### 4.4 顶部状态栏

顶部状态栏显示：

- 当前观察状态：观察中、暂停、跳过敏感内容、模型异常。
- 今日记录数量的用户化表达，例如“今天已整理 6 段工作片段”。
- 暂停按钮。
- 忘掉最近入口。

不要显示太多工程指标，例如 job queue、facts count、confidence unless debug mode。

## 5. 时间轴设计

### 5.1 后台数据与前台呈现分离

后台可以按固定频率或事件生成 observation 和半小时聚合数据。

前台默认不直接展示这些硬切片。

正确方式：

```text
后台 observation / 半小时片段
  -> AI 聚合
  -> 自然工作片段 timelineBlock
  -> 前台时间轴展示
```

### 5.2 时间轴层级

时间轴需要支持三个层级，但 MVP 可以先做前两个。

#### 层级 1：全天概览

用于快速扫一眼。

展示：

- 上午/下午/晚上大致活动节奏。
- 主要项目。
- 工作、沟通、资料、休息等类型的轻量分布。

MVP 可以不用复杂波形，只用简洁的横向/纵向摘要条。

#### 层级 2：默认工作片段

这是主要视图。

展示自然片段，例如：

```text
09:20 - 10:45  整理 Recall 产品体验升级方向
你主要在阅读体验升级文档，并筛选其中适合落地的部分。
相关：Recall、今日页、双轨日报
产出：确认“时间轴中间 + 右侧总结看板”的首页方向
```

#### 层级 3：细节展开

用户点击某个片段后展开。

展示：

- 更细时间点。
- 相关应用/窗口标题。
- 关键截图摘要或文字证据。
- 复制内容、网页标题、文档名。
- 该片段产生的任务/决策。

只有在用户主动展开时，才显示更细的半小时或更细粒度内容。

### 5.3 时间轴卡片字段

前端需要的数据对象建议：

```ts
interface TimelineBlock {
  id: string;
  startAt: string;
  endAt: string;
  title: string;
  summary: string;
  category:
    | "focus_work"
    | "communication"
    | "research"
    | "writing"
    | "coding"
    | "design"
    | "meeting"
    | "admin"
    | "break"
    | "mixed"
    | "unknown";
  projectIds: string[];
  projectNames: string[];
  highlights: string[];
  generatedTasks: string[];
  generatedDecisions: string[];
  reportable: boolean;
  privateRisk: "low" | "medium" | "high";
  sourceSceneIds: string[];
  sourceFactIds: string[];
  sourceObservationIds: string[];
}
```

### 5.4 时间轴文案规则

标题要清楚，不要诗化。

推荐：

- “整理 Recall 产品体验升级方向”
- “处理接口错误并验证修复”
- “阅读竞品资料，提取日报功能参考”
- “与团队确认本周交付范围”

不推荐：

- “深海沉浸”
- “灵感拼图”
- “心流年轮”
- “今日创造印迹”

摘要要温和，但要事实优先。

推荐：

> 这段时间主要在阅读和筛选体验升级建议，重点确认了首页时间轴和双轨日报的方向。

不推荐：

> 你像织网者一样在灵感碎片中穿梭，点亮了今日的创造微光。

## 6. 双轨日报机制

双轨日报是 Recall 面向大众用户的核心价值。

### 6.1 两种报告

#### 我的复盘

给用户自己看。

目标：

- 真实回忆今天。
- 减轻大脑负担。
- 帮用户知道今天做了什么、没做完什么、明天从哪里继续。

可以包含：

- 工作内容。
- 被打断的地方。
- 未完成事项。
- 私人备注。
- 不适合汇报但对自己有用的信息。

语气：

- 温和。
- 真实。
- 不评判。
- 不夸张。

#### 工作日报

给上司、团队、客户或协作者看。

目标：

- 体面。
- 专业。
- 清楚。
- 可复制。
- 不泄露隐私。

只能使用：

- 用户勾选的时间轴片段。
- 用户确认的工作内容。
- 系统判断为 reportable 且 privateRisk 低的内容。

不能包含：

- 私人聊天。
- 娱乐内容。
- 敏感网页。
- 不确定推测。
- 过于口语或情绪化内容。

### 6.2 生成工作日报流程

流程：

1. 用户点击“生成工作日报”。
2. 系统进入选择模式。
3. 时间轴中每个片段出现选择控件。
4. 系统默认预选 reportable=true 且 privateRisk=low 的片段。
5. 用户可手动增删。
6. 右侧显示“将使用 X 个片段生成日报”。
7. 用户点击生成。
8. LLM 只接收被选中的片段和已脱敏内容。
9. 生成日报草稿。
10. 用户编辑、复制或导出。

### 6.3 选择模式 UI

选择模式必须清楚表达：

- 哪些内容会进入日报。
- 哪些内容不会进入日报。
- 用户可以控制。

不要使用复杂动画作为核心表达。

MVP 交互：

- 被选片段高亮。
- 未选片段变淡。
- 右侧实时更新已选数量。
- 提供“仅选工作相关”按钮。
- 提供“清空选择”按钮。
- 提供“预览将发送给 AI 的内容”入口。

### 6.4 报告风格

工作日报提供风格选项：

- 简洁版
- 标准版
- 稍正式

不要一开始提供太多风格。

工作日报结构：

```text
今日完成
- ...

项目进展
- ...

问题与风险
- ...

明日计划
- ...
```

我的复盘结构：

```text
今天主要在做什么
- ...

有价值的进展
- ...

还没收尾的事
- ...

值得以后记住
- ...

明天可以从这里继续
- ...
```

## 7. AI Pipeline 升级

现有 AI Pipeline 可以保留，但输出目标要升级。

不要只生成数据库对象：

- Observation
- Fact
- Scene
- Task
- Report

还要生成前端体验对象：

- TimelineBlock
- DailySummaryPanel
- PersonalReviewDraft
- WorkReportDraft
- UnfinishedThread
- MemoryWorthKeeping
- ReportableHighlight
- PrivateRiskSignal

### 7.1 Observer 升级

Observer 仍然负责看见屏幕，但不要过度文学化。

它应该输出：

- 当前场景。
- 用户可能在做的工作目标。
- 可见内容摘要。
- 关键实体。
- 是否可能涉及私人内容。
- 是否适合汇报。

新增字段建议：

```ts
interface ObserverExperienceFields {
  userFacingSummary: string;
  likelyWorkPurpose: string;
  privacyRisk: "low" | "medium" | "high";
  reportableSignal: "yes" | "maybe" | "no";
}
```

### 7.2 Extractor 升级

Extractor 不仅提取 facts，还要判断 fact 的用途：

- 是否适合时间轴展示。
- 是否适合工作日报。
- 是否适合个人复盘。
- 是否值得长期保存。

新增字段建议：

```ts
interface FactExperienceFields {
  displayUse: Array<"timeline" | "personal_review" | "work_report" | "memory" | "task_list">;
  reportable: boolean;
  privateRisk: "low" | "medium" | "high";
  userValue: "low" | "medium" | "high";
}
```

### 7.3 Timeline Builder

需要新增或明确一个 AI worker：Timeline Builder。

职责：

- 把 scenes/facts/observations 聚合成用户可读的 TimelineBlock。
- 避免机械半小时流水账。
- 保留 source ids。
- 为每个 block 判断 reportable 和 privateRisk。

输入：

- 当天 scenes。
- 当天 facts。
- 活动窗口元数据。
- 半小时聚合指标。

输出：

```ts
interface TimelineBuilderOutput {
  blocks: TimelineBlock[];
  dayStartSummary: string;
  dayMainThread: string;
}
```

### 7.4 Report Writer 拆分

不要再用一个 Reporter 同时写所有报告。

拆成：

1. PersonalReviewWriter
2. WorkReportWriter
3. WeeklyReportWriter
4. MonthlyReportWriter

#### PersonalReviewWriter

输入：

- 今日全部可用 TimelineBlock。
- 待收尾。
- 重要记忆。
- 用户偏好。

允许包含 privateRisk=medium 的内容，但展示时要谨慎。

#### WorkReportWriter

输入：

- 用户勾选的 TimelineBlock。
- reportable=true 的 facts。
- 已脱敏内容。

禁止使用：

- 未勾选片段。
- privateRisk=high 内容。
- 明显私人内容。

输出必须专业、可复制。

### 7.5 Judge 升级

Judge 不要频繁打扰。

它主要生成：

- 待收尾。
- 明日接续。
- 高价值提醒。

不要为普通事实生成大量提醒。

新增输出：

```ts
interface UnfinishedThread {
  id: string;
  title: string;
  reason: string;
  suggestedNextAction: string;
  sourceFactIds: string[];
  sourceTimelineBlockIds: string[];
  priority: "low" | "medium" | "high";
}
```

## 8. Prompt 语气规范

### 8.1 总体语气

Recall 的 AI 语气应该是：

- 温和
- 清楚
- 克制
- 有帮助
- 不评判
- 不肉麻
- 不装熟
- 不像老板
- 不像心理鸡汤

### 8.2 推荐表达

推荐：

- “今天主要在处理...”
- “这段时间集中在...”
- “这里可能还有一件事没收尾...”
- “这几段内容适合整理进工作日报...”
- “明天可以从这里接着看...”

不推荐：

- “辛苦了，创造者”
- “今日颂歌”
- “你点亮了灵感微光”
- “深海沉浸”
- “我一直守护着你”
- “这是属于你的创造印迹”

### 8.3 自己看的复盘语气

可以稍微温和一点，但仍然要事实优先。

示例：

> 今天的主线比较清楚：上午集中在产品体验方向的判断，下午开始把这些判断整理成可执行规格。中间有几处关于日报和时间轴的决策，值得留到后续开发中继续参考。

### 8.4 工作日报语气

专业、简洁、可提交。

示例：

```text
今日完成：
- 梳理 Recall 产品体验升级方向，明确首页采用“时间轴 + 右侧总结看板”的结构。
- 评估外部体验建议，筛选出双轨日报、自然时间轴、报告生成前选择确认等可落地方向。

明日计划：
- 输出统一产品体验升级规格。
- 根据规格拆解前端改造任务。
```

## 9. 前端视觉规范

### 9.1 视觉气质

Recall 应该像一个安静、可信、精致的个人工作空间。

关键词：

- 暖白
- 清晰
- 轻盈
- 克制
- 有呼吸感
- 不像后台
- 不像监控
- 不像聊天机器人

### 9.2 色彩

建议：

- 背景：暖白或浅灰白。
- 主文字：接近黑但不纯黑。
- 次级文字：中性灰。
- 强调色：低饱和青绿。
- 提醒色：柔和琥珀。
- 危险/删除：克制红色。

不要使用大面积紫蓝渐变。

### 9.3 卡片

卡片要清楚承载信息，不要装饰过度。

规则：

- 圆角 8px 左右。
- 细边框优先，少用重阴影。
- 时间轴卡片要有稳定宽度和间距。
- 不要卡片套卡片。
- 操作按钮默认收敛，hover 时出现次级操作。

### 9.4 动效

MVP 动效原则：

- 用轻微过渡提升质感。
- 不做复杂粒子和护盾动画。
- 不让动效影响使用效率。

可做：

- 卡片展开/折叠过渡。
- 选中片段高亮。
- 生成报告时轻量 loading。
- 状态变化轻微 fade。

不做：

- 大量粒子飞行。
- 长时间打字机动画阻碍复制。
- 过度弹跳。
- 大面积发光。

## 10. 隐私和信任表达

### 10.1 正确承诺

可以承诺：

- 数据保存在本机。
- 截图按用户设置本地短期保留。
- 用户自带模型 API Key。
- Recall 不建设自己的云端屏幕历史。
- 工作日报只使用用户选择或确认的内容。
- 用户可以暂停、删除、导出。

不要承诺：

- 所有内容绝不经过云端 AI。
- AI 只处理勾选内容。
- 100% 自动脱敏绝对不会出错。

### 10.2 工作日报生成前预览

生成工作日报前，必须有预览或确认机制。

文案示例：

```text
将使用 6 个工作片段生成日报。
未选择的私人聊天、娱乐网站和敏感内容不会进入本次生成。
```

按钮：

- 生成工作日报
- 返回修改选择
- 预览内容

## 11. 具体页面规格

### 11.1 今日页

中间时间轴卡片内容：

- 时间范围。
- 标题。
- 摘要。
- 项目标签。
- 小型成果标签：任务、决策、资料。
- 选择控件，只有进入“生成工作日报选择模式”时明显显示。

右侧面板：

```text
今日主线
待收尾
今日成果
今日决策
我的复盘 [生成/查看]
工作日报 [选择片段生成]
明天接着做
```

### 11.2 待收尾页

列表分组：

- 今天要看一眼
- 近期未收尾
- 可能已完成，待确认
- 已完成

每条显示：

- 标题。
- 来源时间。
- 所属项目。
- 为什么认为未收尾。
- 建议下一步。

操作：

- 标记完成。
- 稍后。
- 忽略。
- 改项目。
- 查看来源。

### 11.3 报告页

顶部 tabs：

- 我的复盘
- 工作日报
- 周报
- 月报

我的复盘：

- 可一键生成。
- 可以包含更真实的今日记录。
- 默认不用于对外提交。

工作日报：

- 必须从选择模式进入，或使用已确认工作片段。
- 默认结构专业。
- 可复制。
- 可编辑。

周报/月报：

- 默认基于过去已确认的工作日报和项目记忆。
- 不应简单拼接每日流水账。

### 11.4 项目页

项目详情包含：

- 项目概览。
- 最近进展。
- 时间轴。
- 待收尾。
- 决策。
- 资料。
- 人物。
- 可生成项目报告。

### 11.5 记忆库

搜索结果卡片显示：

- 类型。
- 标题。
- 摘要。
- 时间。
- 项目。
- 来源。

支持自然语言搜索，但回答必须基于检索结果。

### 11.6 信任中心

必须包含：

- Recall 观察什么。
- 截图保存多久。
- 模型 API 如何调用。
- 工作日报如何保证只用选中内容。
- 如何暂停。
- 如何删除。
- 如何导出。

## 13. Prompt 输出补充

### 13.1 Timeline Builder Prompt 目标

输入当天 scenes/facts/observations 后，输出 TimelineBlock。

要求：

- 标题清楚。
- 摘要温和但事实优先。
- 不使用诗意标签。
- 每个 block 必须有 source ids。
- 判断 reportable。
- 判断 privateRisk。

### 13.2 Work Report Prompt 目标

只基于用户选择内容生成。

要求：

- 专业。
- 可复制。
- 不泄露隐私。
- 不编造成果。
- 不提未选择内容。
- 不出现“我看到你...”这种自用语气。

### 13.3 Personal Review Prompt 目标

基于当天较完整记忆生成。

要求：

- 真实。
- 温和。
- 帮用户回忆。
- 帮用户把未完成事项留给明天。
- 可以包含“这件事可能还没收尾”这样的不确定表达。

## 15. 验收标准

### 15.1 今日页验收

通过标准：

- 用户一打开就能看懂今天做了什么。
- 中间时间轴不是后台日志。
- 右侧能看到今日主线和待收尾。
- 不显示 L0/L1/L2/Fact/Scene 等技术词。
- 不制造监控感。

### 15.2 双轨日报验收

通过标准：

- 可以生成我的复盘。
- 可以生成工作日报。
- 工作日报生成前能选择片段。
- 未选择片段不进入工作日报 prompt。
- 生成结果可编辑、复制。
- 工作日报语气专业，不像鸡汤。

### 15.3 AI 输出验收

通过标准：

- AI 能生成 TimelineBlock。
- AI 能判断 reportable。
- AI 能判断 privateRisk。
- AI 能生成待收尾。
- AI 能分别生成自用复盘和工作日报。
- 每个重要输出有 source ids。

### 15.4 视觉体验验收

通过标准：

- 页面不像后台管理系统。
- 页面不花哨。
- 字体、间距、卡片层级清楚。
- 主要操作容易发现。
- 动效轻，不影响效率。

### 15.5 隐私验收

通过标准：

- 用户知道截图保存多久。
- 用户知道模型 API 会被调用。
- 用户知道工作日报使用哪些内容。
- 用户可以暂停。
- 用户可以忘掉最近。
- 用户可以删除数据。

## 16. 最终产品判断标准

如果用户一天结束后打开 Recall，能自然完成下面这件事，说明升级成功：

1. 看一眼时间轴，想起今天的主要工作。
2. 看右侧待收尾，知道明天从哪里继续。
3. 点一下生成自己的复盘，帮助自己清空大脑。
4. 勾选工作片段，生成一份能发给上司/团队的日报。
5. 相信这些记忆以后还能被找回来。

如果页面只是展示很多数据、很多 AI 术语、很多工程状态，即使后端能力强，也不算成功。
